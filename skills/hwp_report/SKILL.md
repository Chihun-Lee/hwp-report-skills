# 연구보고서 (hwpx) — 설정 → spec → 빌드 → 게이트 → 검수 → 작성자 수정 왕복

실제 연차점검 보고서를 작성자와 함께 완성한 과정(초안 → 작성자가 한컴에서 직접 고친 확정본)을 코드로 옮긴 스킬이다.
**원본은 spec(YAML)이고, hwpx는 결과물이다.** 작성자가 hwpx를 고치면 그 수정을 spec으로 거둬들인 뒤 다음 판을 만든다.

명령은 모두 `scripts/hwp_report.sh`로 실행한다. 아래에서 `HR`은 `bash <이 스킬 폴더>/scripts/hwp_report.sh`를 뜻한다.
사용자별 설정·문체·양식은 `~/.hwp_report/`에 있다. 스킬을 업데이트해도 이 폴더는 남는다.

| 파일 | 내용 |
|---|---|
| `references/writing_rules.md` | ⭐ **기본 문체·서식 규칙**과 작성자 수정 유형 대조표. 작성 전에 반드시 읽는다 |
| `references/style_guide.md` | 내 문체 만들기 절차와 `style.md` 틀 |
| `references/forms.md` | 다른 양식 등록·`sections:`/`tables:`로 채우기 |
| `references/spec.md` | spec 문법: 개조식 마크업, 표, 그림 |
| `references/form_map.md` | 기본 양식 구조, 요약표 칸 주소 |
| `references/layout.md` | 그림 크기 규약, 검수 순서, 한컴 PDF 함정, 왕복 절차 |
| `references/figure_rules.md` | 실데이터 그림 규칙(요약). 상세는 `report-figure` 스킬 |
| `examples/report.example.yaml` | 기능을 모두 쓰는 예시 spec(가상 과제) |
| `assets/forms/annual_review_2026/` | 기본 양식(form.hwpx)과 프로필(profile.yaml) |
| `templates/figstyle.py` | matplotlib 그림 스타일(Arial + 나눔고딕, 400 dpi) |

## 0. 설치 확인

- `HR selftest`가 「selftest OK」로 끝나면 된다.
- 「파이썬 패키지 없음」이 나오면 `bash <스킬>/scripts/setup.sh`를 실행한다. `~/.hwp_report/venv`에 lxml·pyyaml·pillow·numpy를 설치한다.
- **필수**: Python 3.9+.
- **선택**: node 18+와 rsvg-convert(미리보기), poppler(쪽 빈칸 측정·PDF 문체 샘플), macOS 한컴오피스(PDF 최종 확인).

## 1. 처음 쓸 때 — 문체·양식 고르기 (설정이 없으면 반드시)

`HR config show`를 실행한다. 「설정 없음」(종료 코드 3)이면 **AskUserQuestion으로 두 가지를 묻는다.**

1. **문체**
   - 「기본 문체 (권장)」 — 기관 보고서 표준 개조식(`writing_rules.md`)
   - 「내 문체 만들기」 — 내가 쓴 보고서 3~10개를 주면 분석해서 만듦
   - 「설치된 문체 스킬」 — 예: `style-ko-report-bullet`
2. **양식**
   - 「기본 양식 (권장)」 — 연차점검 보고서 양식1 구조(예시 양식). 기관에서 받은 실제 양식1 hwpx가 있으면 「다른 양식 주기」로 등록하면 같은 규칙으로 맞는다
   - 「다른 양식 주기」 — hwpx 파일을 받아 등록

고른 대로 처리한다.
- `HR config init --style default|personal|skill:<이름> --form default`
- **내 문체 만들기**: `references/style_guide.md` 절차대로 진행한다. 샘플 받기 → `HR style 파일…` → 원문 읽기 → `~/.hwp_report/style.md` 작성 → 예문으로 확인 → `HR config set style personal`.
- **다른 양식**: `references/forms.md` 절차대로 진행한다. `HR config add-form 양식.hwpx --name <이름>` → 분석 결과를 사용자와 함께 보고 profile·spec 방식을 정한다.

**설정을 바꾸고 싶다고 하면**(「문체 바꿔줘」, 「양식 바꿔줘」) 같은 질문을 다시 하고 `HR config set …`을 실행한다.

### 문체 적용 규칙

- 본문을 쓰기 전에 `HR config style-path`가 가리키는 가이드를 읽고 따른다.
- **personal / skill:** 이 가이드가 `writing_rules.md`의 A·B(문체·내용 선별)보다 먼저다. C(서식)·E(작업 방식)는 그대로 지킨다.
- **default:** `writing_rules.md` 전체를 따른다.
- 게이트(`HR check`)는 문체에 따라 규칙을 바꾼다.
  - default: 기본 문체 규칙
  - personal: `style.md` 맨 위의 `lint:`

## 2. 시작할 때 — 먼저 확인할 것

1. **작업 폴더에 작성자가 고친 hwpx가 있는지 본다.** 수정 시각이 내 마지막 빌드보다 늦은 hwpx나 `_vNN` 파일이 있으면 그것이 최신본이다.
   - 그때는 새로 쓰지 말고 **7절 왕복**부터 한다. 다시 빌드해서 작성자 수정을 덮어쓰는 것이 이 작업에서 가장 큰 사고다.
   - 한컴에 열려 있는 문서는 저장하고 창을 닫아 달라고 한 뒤에 다룬다.
2. **근거 문서를 모은다.**
   - 계획서 진본: 최종목표, 연차별 목표, 주요 연구내용, 성과목표, 다음 연도 계획
   - 작성 분담: 내가 쓸 부분과 다른 작성자 몫
   - 성과 원자료: 측정값, 장비 로그, 구매·심의 상태
   - 지난 점검의 지적사항
3. 분담이 나뉘어 있으면 다른 사람 몫은 `※ … ○○○ 작성분으로 수합` 자리표시로 남긴다.

## 3. spec 쓰기

1. `examples/report.example.yaml`을 작업 폴더로 복사해 시작한다. 문법은 `references/spec.md`에 있다.
   - 다른 양식이면 `references/forms.md`의 `sections:`/`tables:` 예시로 시작한다.
2. **본문은 1절의 문체 규칙을 따른다.** 기본 문체의 핵심은 다음과 같다.
   - 개요·목표는 **계획서 문장을 그대로 인용**한다. 개조식 명사형 종결로 쓰고 마침표를 찍지 않는다.
   - 2장은 `## (세부기술N) 절 제목` → `-` 성과 → `·` 근거 수치 → `[그림 ID] 캡션` 순서로 쓴다.
   - 「무인」 대신 「자동화」를 쓴다. 업체명·「협력팀」은 쓰지 않는다. 괄호와 날짜는 최소로 쓴다. 본문에서 그림을 괄호로 언급하지 않는다.
   - 핵심 수치만 남긴다. 검토만 하고 결론이 없는 내용과 다음 연차 내용은 성과 절에 넣지 않는다. 얇은 절은 합친다.
3. 사실(구매 진행 상태, 실증 횟수 등)은 제출 시점 값으로 쓴다. 모르면 작성자에게 묻는다.
4. **진도율·자체평가·성과 실적 수치는 책임자가 확정한다.** 추정해서 넣은 값은 넘길 때 목록으로 알린다.
5. 개인정보(연락처·국가연구자번호)는 요약표 칸에만 넣는다. spec을 남에게 줄 때는 그 칸을 지운다.

## 4. 그림

- 실데이터 논문식 figure만 쓴다. AI 생성 이미지와 픽토그램은 쓰지 않는다.
  - 작성자가 지정한 AI 렌더만 예외로 넣고, 캡션에 「(AI 생성 이미지)」를 붙인다.
- 한국어 보고서면 그림 안 글자도 한글로 쓴다.
- 400 dpi jpg로 만들어 spec의 `figures` 폴더에 둔다. 파일 이름이 곧 그림 ID다.
- 문서 상한은 150 × 105 mm이고, 캡션은 엔진이 `<…>`로 붙인다.
- 규칙은 `references/figure_rules.md`, 만드는 절차는 `report-figure` 스킬에 있다.

## 5. 빌드 → 게이트

```bash
HR build report.yaml -o 보고서_vNN.hwpx            # 양식은 spec form: → 설정 form 순서
HR check 보고서_vNN.hwpx --spec report.yaml        # ERROR 0이어야 넘김. WARN은 하나씩 읽고 판단
```

- **빌드 WARN**: 「양식에 ○○ 자리가 없어 …」가 나오면 그 내용은 문서에 들어가지 않은 것이다. 양식 프로필이나 `sections:`로 자리를 잡는다.
- **게이트가 잡는 것**
  - 구조: zip·mimetype, XML, 스타일 참조, 그림 파일
  - 문체 규칙: 1절 참조
  - 공통: 남은 자리표시, 캡션 형식, 목차 쪽번호, 다음 연차 내용, 금지어
- 양식에 원래 있던 글자는 검사하지 않는다.

## 6. 검수 (넘기기 전 필수)

1. `HR render 보고서.hwpx`로 헤드리스 미리보기를 만들고 `*_render/pair_*.png`를 **직접 열어 본다**.
   - 표 칸, 그림, 캡션, 빈 줄, 들여쓰기를 확인한다.
   - ⚠️ rhwp는 큰 그림이 쪽 경계에 걸리면 뒤 내용을 빠뜨린다. 쪽 수나 쪽 나눔은 판단하지 않는다.
2. **한컴 PDF**로 실제 쪽 배치를 확인한다: `HR pdf 보고서.hwpx` (macOS).
   - 사용자가 입력 중이면 기다린다. 유휴 시간은 `ioreg -c IOHIDSystem`의 HIDIdleTime으로 본다.
   - 업데이트 창이나 복구 창이 뜨면 `references/layout.md`를 본다.
   - 한컴에서 열 때 손상·복구 경고가 없어야 한다.
3. `HR fill 보고서.pdf --hwpx 보고서.hwpx`로 쪽 아래 빈칸이 큰 곳을 찾는다.
   - 큰 그림이 밀린 탓이면 다음 중 하나로 고친다: `[그림 ID 폭=110]`으로 폭 줄이기, 그림 분할, 문단 순서 조정.
4. **넘길 때 함께 알린다**: 산출물 경로, 게이트 결과, 추정치·확인 필요 목록, 남은 자리표시.

## 7. 작성자가 한컴에서 고친 뒤 (왕복)

```bash
HR extract 수정본.hwpx -o report.yaml --spec 이전report.yaml   # 수정본 → spec (그림·양식·sections는 이전 spec에서 이어받음)
HR build report.yaml -o 재빌드.hwpx
HR diff 재빌드.hwpx 수정본.hwpx                                  # 「동일」이어야 spec이 수정본을 다 담은 것
```

1. **「동일」이 나오면** 이제 spec을 고쳐 다음 판(`_v02` …)을 빌드해도 작성자 수정이 살아 있다.
2. **차이가 남으면** spec으로 표현할 수 없는 수정이다(글자 모양을 손으로 바꾸는 등).
   - 이때는 다시 빌드하지 말고 수정본 hwpx에 직접 패치한다.
   - 그 차이를 작성자에게 알린다.
3. `HR diff 이전빌드.hwpx 수정본.hwpx`로 **작성자가 무엇을 고쳤는지** 읽는다.
   - 같은 종류의 수정이 반복되면 규칙으로 남기라고 제안한다. 내 문체면 `~/.hwp_report/style.md`, 기본 문체면 `writing_rules.md`에 넣는다.
4. 작성자 수정본은 작업 폴더의 `_사용자수정본/`에 시각을 붙여 백업한다.

## 하지 말 것

- 상신·제출·메일 발송·업로드는 하지 않는다. hwpx·PDF 파일까지만 만든다.
- 작성자가 한컴에서 고친 파일을 다시 빌드한 파일로 덮어쓰지 않는다. 7절을 먼저 한다.
- 진본 폴더(계획서·예산 등 「수정금지」)의 파일을 고치지 않는다. 양식도 복사본을 쓴다.
- 근거 없는 수치를 쓰지 않는다. 진도율이나 등급을 「확정」처럼 쓰지 않는다.
- 내 문체 예시에 샘플에 없는 문장을 지어내지 않는다.

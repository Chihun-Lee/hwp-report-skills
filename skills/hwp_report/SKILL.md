# 국책 연구보고서 (hwpx) — 근거 → 원고 → 빌드·병합 → 게이트 → 한컴 검수 → 작성자 수정 학습

국책 R&D 연차보고서 두 건을 작성자와 끝까지 완성한 과정을 코드와 규칙으로 옮긴 스킬이다.
한 건은 단독 연차점검 보고서(초안 → 작성자 수정 → 수합 → 제출)이고, 다른 한 건은 주관기관 통합 양식에 공동기관 파트를 넣은 연차보고서(10여 판, 작성자 수정 2회, 1차 취합 → 최종)다.
**원본은 spec·원고이고 hwpx는 결과물이다.** 작성자가 hwpx를 고치면 그 수정을 먼저 거둬들이고, 무엇을 고쳤는지 읽어 규칙으로 남긴 뒤 다음 판을 만든다.

명령은 모두 `scripts/hr.py` 하나로 실행한다(macOS·Windows·Linux 공통). 아래에서 `HR`은 다음을 뜻한다.

| 환경 | `HR` |
|---|---|
| macOS·Linux | `python3 "<이 스킬 폴더>/scripts/hr.py"` |
| Windows (Git Bash·PowerShell) | `py -3 "<이 스킬 폴더>/scripts/hr.py"` — `py`가 없으면 `python`, 둘 다 안 되면 `"$HOME/.hwp_report/venv/Scripts/python.exe"` |

- hr.py는 `~/.hwp_report/venv`의 파이썬을 알아서 골라 쓰므로, 어떤 파이썬으로 불러도 된다. 예전 `bash scripts/hwp_report.sh <명령>`도 그대로 동작한다.
- Windows 경로는 `/`로 써도 된다(`C:/Users/…/보고서.hwpx`). 공백·한글이 든 경로는 큰따옴표로 감싼다.
- 사용자별 설정·문체·양식·실제 사례 노트는 `~/.hwp_report/`(Windows: `C:\Users\<이름>\.hwp_report\`)에 있다. 스킬을 업데이트해도 이 폴더는 남는다.

## 0. 설치 확인

- `HR selftest`가 「selftest OK」로 끝나면 된다. `HR doctor`는 버전과, 무엇이 되고 무엇이 빠졌는지 보여 준다.
- 사용자가 「hwp_report 업데이트해줘」, 「스킬 최신으로」라고 하면 `HR update`를 실행한다(timeout 10분). 최신본을 받아 다시 설치하고 자가검사까지 한다. 끝나면 Claude Code를 다시 시작해야 새 판이 쓰인다고 알린다.
- 이 스킬을 처음 설치하는 절차(레포 링크를 받았을 때)는 레포의 `INSTALL.md`에 있다.
- **외부 API 키**: 지금 기능은 모두 API 키 없이 동작한다. 그래서 설치할 때나 처음 쓸 때 키를 묻지 않는다. 어떤 기능이 API 키를 써야 할 때만 다음을 따른다(사용자가 외부 서비스 연동을 요청한 경우 등).
  1. `HR key get <키 이름>`의 종료 코드를 본다.
     - 0: 키가 있다. 출력값을 쓴다.
     - 4: 사용자가 없다고 했다. **묻지 않고 그 기능만 건너뛰고** 나머지 작업을 계속한다.
     - 3: 아직 물은 적이 없다. 2번으로 간다.
  2. AskUserQuestion으로 한 번만 묻는다. 선택지는 「키 있음 — 붙여 넣기」와 「없음 — 이 기능 빼고 진행」이다.
  3. 키가 있으면 `printf %s '<키>' | HR key set <키 이름>`, 없으면 `HR key skip <키 이름>`을 실행한다.
     - 키는 `~/.hwp_report/keys.json`에만 둔다. spec·보고서·md·레포에는 쓰지 않는다.
     - 건너뛴 기능은 결과 보고에 한 줄로 알린다.
- 「파이썬 패키지 없음」이 나오면 **사용자에게 묻지 않고 `HR setup`을 실행한다**(1~2분). `~/.hwp_report/venv`에 lxml·pyyaml·pillow·numpy·PyMuPDF(+Windows는 pywin32)를 설치하고 끝에 `doctor`를 보여 준다. 스킬 폴더·전역 파이썬은 건드리지 않는다.
  - pip가 SSL·프록시 오류로 실패하면(회사망) `HR setup --pip-args "--trusted-host pypi.org --trusted-host files.pythonhosted.org"`.
  - 「Python 3.9 이상 필요」·`python`을 못 찾으면 사용자에게 설치를 안내한다. Windows: `winget install -e --id Python.Python.3.12` 또는 python.org(「Add python.exe to PATH」 체크).
  - 보고서 그림까지 만들면 `HR setup --figures`(matplotlib).
- **필수**: Python 3.9+.
- **선택**: 한컴오피스 한글(PDF 최종 확인 — Windows는 COM, macOS는 한컴오피스 앱), node 18+(헤드리스 미리보기).

## 1. 처음 쓸 때 — 문체·양식 고르기 (설정이 없으면 반드시)

`HR config show`를 실행한다. 「설정 없음」(종료 코드 3)이면 **AskUserQuestion으로 두 가지를 묻는다.**

1. **문체**
   - 「기본 문체 (권장)」 — 국책 보고서 개조식(`writing_rules.md`)
   - 「내 문체 만들기」 — 내가 쓴 보고서 3~10개를 주면 분석해서 만듦
   - 「설치된 문체 스킬」 — 예: `style-ko-report-bullet`
2. **양식**
   - 「기본 양식 (권장)」 — 연차점검 보고서 양식1 구조(예시 양식). 기관에서 받은 실제 양식이 있으면 「다른 양식 주기」로 등록한다
   - 「다른 양식 주기」 — hwpx 파일을 받아 등록

고른 대로 처리한다.
- `HR config init --style default|personal|skill:<이름> --form default`
- **내 문체 만들기**: `references/style_guide.md` 절차. 샘플 받기 → `HR style 파일…` → 원문 읽기 → `~/.hwp_report/style.md` → 예문으로 확인 → `HR config set style personal`.
- **다른 양식**: `references/forms.md` 절차. `HR config add-form 양식.hwpx --name <이름>` → 분석 결과를 사용자와 함께 보고 profile·spec 방식을 정한다.

**설정을 바꾸고 싶다고 하면**(「문체 바꿔줘」, 「양식 바꿔줘」) 같은 질문을 다시 하고 `HR config set …`을 실행한다.

### 문체 적용 규칙

- 본문을 쓰기 전에 `HR config style-path`가 가리키는 가이드를 읽고 따른다.
- **personal / skill:** 이 가이드가 `writing_rules.md`의 A·B보다 먼저다. C(서식·문서 프로필)·E(작업 방식)·F(표 칸)·G(잔여물)는 그대로 지킨다.
- **default:** `writing_rules.md` 전체와 `national_report_guide.md`를 따른다.
- `~/.hwp_report/notes/`에 실제 사례 노트(작성자 수정 전후 문장, 최종본 모범 문단)가 있으면 함께 읽고 문장 견본으로 쓴다. 이 노트의 문장은 공개 문서에 옮기지 않는다.

## 2. 시작할 때 — 먼저 확인할 것

1. **작업 폴더에 작성자가 고친 hwpx가 있는지 본다.**
   - mtime이 마지막 빌드보다 늦은 hwpx, `_사용자수정`·`_vNN` 파일, 빌드 폴더에서 그 자리에서 고친 파일(`content.hpf`의 마지막 저장자가 엔진이 아님)이 최신본이다.
   - 그때는 새로 쓰지 말고 **7절**부터 한다. 다시 빌드해서 작성자 수정을 덮어쓰는 것이 가장 큰 사고다.
   - 한컴에 열려 있는 문서는 저장하고 창을 닫아 달라고 한 뒤에 다룬다(검수 PDF는 사본으로 뽑으므로 열려 있어도 된다).
2. **어떤 일인지 고른다** (`national_report_guide.md` 0절).
   | 경우 | 갈래 |
   |---|---|
   | 단독 양식을 처음부터 채움 | 3~6절 (spec → build) |
   | 주관기관이 보낸 통합 양식에 우리 칸만 채움 | `consortium_merge.md` → 6절 검수 |
   | 수합본·통합본의 일부 블록만 고침(다음 연도 계획, 일정표 등) | 작성자 최신본에 패치 스크립트(`hwpx_patch.py`) |
   | 제출 뒤 바뀐 내용을 보냄 | 「추가 파트 + 배치표」 또는 한 장짜리 「수정 내용」 문서 |
3. **근거 문서를 모은다.**
   - 계획서 진본: 최종목표, 연차별 목표, **세부기술 정식 명칭과 당해 연구내용 문구**, 성과지표, 다음 연도 계획(쪽 번호를 적어 둔다)
   - 작성 분담: 내가 쓸 부분과 다른 작성자·기관 몫
   - 성과 원자료: 측정값, 장비 로그, 구매·심의 상태, 같은 과제 다른 세션의 최신 산출물(경로 확인)
   - 지난 점검의 지적사항 **원문**과 출처, 주관기관 메모(`HR dump 양식.hwpx --memos`)
   - 같은 작성자의 확정 보고서가 있으면 통계 비교 기준으로 쓴다(`writing_rules.md` E5)
4. **문서 프로필을 정한다**(`writing_rules.md` C절): 캡션 꼴·위치, 자동 글머리 여부, 약어 풀이, 종결, 날짜·이정표 꼴, 과제 용어. 남의 글이 있으면 그 글에서 센다. spec의 `caption_format`·`caption_mode`·`lint:`에 적는다.
5. 분담이 나뉘어 있으면 다른 사람 몫은 `※ … ○○○ 작성분으로 수합` 자리표시로 남긴다.
6. 여러 단계로 이어지는 작업이면 작업 폴더에 `_진행상황.md`를 두고 판마다 갱신한다(요청 원문, 마감 두 개, 결정, 다음 할 일).

## 3. 원고 쓰기

1. 단독 양식은 `examples/report.example.yaml`을 작업 폴더로 복사해 시작한다. 문법은 `references/spec.md`.
   - 다른 양식이면 `references/forms.md`의 `sections:`/`tables:` 예시로 시작한다.
2. **장·절마다 `national_report_guide.md`의 틀을 따른다.** 핵심만 추리면:
   - 제목 단계는 **계획서 문구 그대로**. ❍ = 세부기술 정식 명칭, - = 당해 연구내용 문구, ‧ = 실적(단독 양식). 내가 지은 소제목·약칭을 쓰지 않는다.
   - 묶음마다 **첫 줄은 목적, 끝 줄은 의의**. 기능 문장에는 쓸모 꼬리(「~하여 ~ 가능」, 「~와 연계할 수 있음」).
   - **실제로 한 방법·결과만** 쓴다. 계획서 방법 문장을 실적처럼 옮기지 않는다.
   - 성과지표 수치·주 모델 이름·성능 사이클 시간은 남기고, 범위는 상한·비율로, 보조 도구 이름은 기능으로 낮춘다. 비교 우위·안정성은 숫자로, 약한 지표·오분류·한계·향후 계획은 뺀다.
   - 「라벨: 내용」 콜론, 화살표, 줄 머리 「(라벨)」, 풀이 괄호(문서 프로필이 never일 때), 날짜(교육 실적·행정 이정표·양식 칸 제외)를 쓰지 않는다.
   - 불리한 경과·실패 건수·확정 전 수량·작은 시연 규모는 쓰지 않는다. 빼는 것이지 바꾸는 것이 아니다.
   - 문장은 한 줄에 맞게 짧게(공백 빼고 약 38자 안, 또는 확실히 두 줄), 주 내용 절은 넉넉하게.
3. **큰 보고서는 파트별로 나눠 쓴다**(`writing_rules.md` E4): 파트마다 원고(json/yaml) + 근거 md(출처·확인 필요)를 파일로 받고, 조립은 한 곳에서만 한다.
4. 사실(구매 진행 상태, 실증 횟수 등)은 제출 시점 값으로 쓴다. 모르면 작성자에게 묻는다.
5. **진도율·자체평가·실적 수치는 책임자가 확정한다.** 미확정은 `○○`로 두고 칸 단위로 채운다(일괄 치환 금지).
6. 개인정보(연락처·국가연구자번호)는 요약표 칸에만 넣는다. spec을 남에게 줄 때는 그 칸을 지운다.

## 4. 그림

- 실데이터 논문식 figure만 쓴다. AI 생성 이미지와 픽토그램은 쓰지 않는다. 작성자가 지정한 AI 렌더만 예외로 넣고, 그림 안에 「AI 생성」을 표시한다.
- 흰 배경, 그림 안 소제목·표 없음, 그래프는 테두리·눈금선 없음·안쪽 범례·한글 축·핵심 수치 표기, 문서 안 그래프 양식 통일.
- 수행 과정 장에는 방법 그림, 결과·요약 절에는 결과·개념도(본문 그림 재사용 금지). 장비는 심의결과서·입찰공고·설치 사진, 교육은 현장 사진 + 서명록.
- 수정 가능한 PPT로 달라고 하면 `HR figs`로 만든다(`references/figure_ppt.md`). 그림 1개 = 슬라이드 1장(네이티브 차트·도형), 보고서용 jpg도 함께 나온다. 작성자가 고친 PPTX는 `HR figs --from 고친.pptx`로 다시 뽑는다.
- 400 dpi jpg로 만들어 spec의 `figures` 폴더에 둔다. 파일 이름이 곧 그림 ID다. 문서 상한은 150 × 105 mm.
- 규칙은 `references/figure_rules.md`, 만드는 절차는 `report-figure` 스킬에 있다.

## 5. 빌드 → 게이트

```bash
HR build report.yaml -o claude_iteration/vN_MMDD/보고서.hwpx     # 양식은 spec form: → 설정 form 순서
HR check 보고서.hwpx --spec report.yaml                         # ERROR 0이어야 넘김. WARN은 하나씩 읽고 판단
HR check 통합본.hwpx --form 주관기관양식.hwpx                    # 통합 양식: 모든 구역, 남의 글은 빼고 우리 글만
```

- **빌드 WARN**: 「양식에 ○○ 자리가 없어 …」가 나오면 그 내용은 문서에 들어가지 않은 것이다. 양식 프로필이나 `sections:`로 자리를 잡는다.
- **게이트가 잡는 것**: 구조(zip·mimetype, XML, 스타일 참조, 그림 파일) / 문체 규칙(`writing_rules.md` ★: 날짜, 괄호, 콜론 라벨, 화살표, 과장, 「단계임」, 약한 지표, 시간 범위, 상호참조, 약어 풀이) / 잔여물(tbd, 「반영 예정」, `○○`, 낱자모, 쉼표 앞 공백, 숫자 % 띄움, 양식 자리표시) / 캡션 형식 / 목차 쪽번호 / 다음 연차 내용 / 금지어·과제 용어(spec `lint:`).
- 양식에 원래 있던 글자는 검사하지 않는다.
- 결과는 새 판 폴더 `claude_iteration/vN_MMDD/`에 둔다. 이전 판을 덮어쓰지 않는다.

## 6. 검수 (넘기기 전 필수)

1. `HR render 보고서.hwpx`로 헤드리스 미리보기를 만들고 `*_render/pair_*.png`를 **직접 열어 본다**. 표 칸, 그림, 캡션, 빈 줄, 들여쓰기를 본다.
   - node가 없으면 건너뛰고 2로 간다(선택 기능).
   - ⚠️ rhwp는 큰 그림이 쪽 경계에 걸리면 뒤 내용을 빠뜨린다. 쪽 수·쪽 나눔·줄바꿈은 판단하지 않는다.
2. **한컴 PDF**: `HR pdf 보고서.hwpx` → 같은 폴더에 `보고서.pdf`. 원본이 아니라 `HRQA_…` 사본을 열어 PDF만 뽑는다.
   - **Windows**: 한글을 COM으로 새로 띄워(창 숨김) 사본을 열고 PDF로 저장한 뒤 그 문서만 버리고 닫는다. 사용자가 열어 둔 한글 창은 건드리지 않는다. 「파일 접근 허용」 창이 뜨면 사용자에게 「모두 허용」을 눌러 달라고 한다(setup이 보안 모듈을 등록해 두면 뜨지 않는다). 종료 코드 5 = 한글 COM 없음, 6 = 열기·저장 실패, 7 = 시간 초과(숨은 확인 창).
   - **macOS**: `HR pdf 보고서.hwpx [대기초]`. 사용자가 입력 중이면 입력이 멈출 때까지 기다리고 HRQA 창만 닫는다. 화면이 꺼져 있거나 잠겨 있으면 종료 코드 3 — 「한컴 쪽 확인 대기」로 보고하고 화면이 켜진 뒤 다시 돌린다.
   - 한글이 없으면 사용자에게 한글에서 「PDF로 저장」해 달라고 하고, 받은 PDF로 3·4를 한다.
   - 한컴에서 열 때 손상·복구 경고가 없어야 한다. 함정은 `references/layout.md`.
3. **꼬리 줄**: `HR tail 보고서.pdf --hwpx 보고서.hwpx [--skip-form 원본양식.hwpx]` → 0개가 될 때까지 문장을 줄이고 다시 PDF.
4. **쪽 빈칸**: `HR fill 보고서.pdf --hwpx 보고서.hwpx` → 큰 그림이 밀린 곳은 폭 줄이기·그림 나누기·문단 순서 조정. 제목이 쪽 끝에 홀로 남으면 다음 문단과 붙인다.
5. **넘길 때 함께 알린다**(`national_report_guide.md` 5절): 산출물 절대경로, 게이트·꼬리 줄·한컴 확인 결과(안 본 것은 안 봤다고), 추정치·남은 `○○`·확인 필요 목록, 바꾼 남의 글, 처리 안 한 주관기관 메모. 본문이 끝나면 제출물 목록(별첨·장비카드·진단표 등)과 대조한 빈칸 목록도.
6. `★현재최종본/`은 작성자가 확인하거나 지시했을 때만 바꾼다.

## 7. 작성자가 한컴에서 고친 뒤 (왕복 + 학습)

```bash
HR learn 이전빌드.hwpx 수정본.hwpx -o 수정포인트.md           # 무엇을 어떻게 고쳤나: 유형별 횟수·반복 치환·전후 표
HR extract 수정본.hwpx -o report.yaml --spec 이전report.yaml   # 수정본 → spec (그림·양식·sections는 이전 spec에서 이어받음)
HR build report.yaml -o 재빌드.hwpx
HR diff 재빌드.hwpx 수정본.hwpx                                  # 「동일」이어야 spec이 수정본을 다 담은 것
```

1. 수정본은 `claude_iteration/vN_MMDD_사용자수정/`(또는 `_사용자수정본/`에 시각을 붙여) 보관하고, 다음 판은 그 파일을 바탕으로 만든다.
2. **`HR learn`으로 수정 포인트를 읽는다.**
   - 같은 유형이 두 번 넘게 나오면 규칙으로 남기자고 제안한다. 기본 문체면 `writing_rules.md`(공개용으로 바꿔 쓴 예시), 내 문체면 `~/.hwp_report/style.md`.
   - 실제 문장이 든 `수정포인트.md`는 작업 폴더와 `~/.hwp_report/notes/`에 둔다.
   - 기계로 잡을 수 있는 반복(같은 낱말 치환 등)은 spec `lint.replace`나 `lint.forbid`에 넣는다.
3. **「동일」이 나오면** 이제 spec을 고쳐 다음 판을 빌드해도 작성자 수정이 살아 있다.
4. **차이가 남으면** spec으로 표현할 수 없는 수정이다(글자 모양을 손으로 바꾸는 등). 다시 빌드하지 말고 수정본 hwpx에 직접 패치하고, 그 차이를 작성자에게 알린다.
5. 통합 양식처럼 spec이 없는 문서는 수정본에 **필요한 블록만** 패치한다. 패치 뒤 `HR diff 수정본 결과`로 의도한 곳만 바뀌었는지 확인한다.

## 하지 말 것

- 상신·제출·메일 발송·업로드는 하지 않는다. hwpx·PDF 파일까지만 만든다.
- 작성자가 한컴에서 고친 파일을 다시 빌드한 파일로 덮어쓰지 않는다. 7절을 먼저 한다.
- 주관기관·다른 작성자의 글·표 값·메모를 바꾸지 않는다. 바꿔야 하면(연차 표기 오류 등) 고친 안과 함께 알린다.
- 자리표시(`○○`)를 문서 전체에서 일괄 치환하지 않는다.
- 진본 폴더(계획서·예산 등 「수정금지」)의 파일을 고치지 않는다. 양식도 복사본을 쓴다.
- 근거 없는 수치를 쓰지 않는다. 진도율이나 등급을 「확정」처럼 쓰지 않는다. 계획서 방법을 실적처럼 쓰지 않는다.
- 내 문체 예시에 샘플에 없는 문장을 지어내지 않는다. 실제 사례 노트의 문장을 공개 문서·예시에 옮기지 않는다.
